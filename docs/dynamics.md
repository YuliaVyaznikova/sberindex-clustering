# Динамика

Как прослеживаются изменения типов МО во времени. Код в `src/dynamics.py`, запуск `python run.py track`, параметры в разделах `model` и `dynamics` файла `config.yaml`.

## Шаг по времени

Сеть строится для каждого окна «скользящий год» с концом в квартале: 2023Q4 (весь 2023 год), 2024Q1, 2024Q2, 2024Q3, 2024Q4 (весь 2024 год). Соседние окна сдвинуты на квартал. Сравнение 2023Q4 и 2024Q4 это сравнение двух непересекающихся календарных лет.

Отдельные кварталы для динамики не годятся:
- доли трат по категориям сезонны, и у разных МО сезонность разная (доля здоровья растёт весной, маркетплейсы в четвёртом квартале), поэтому положение МО относительно других меняется от квартала к кварталу без изменений в экономике;
- данные Росстата идут нарастающим итогом и обнуляются в январе, а демография и миграция на стыке лет переключаются на следующий год.

Поэтому между отдельными кварталами признаки сдвигаются на 0.23-0.40 стандартного отклонения (траты) со скачками на стыке лет, а между окнами скользящего года на 0.10-0.14, без скачков. Что дали бы типы по отдельным месяцам, показано в [economy.md](economy.md).

## Подходы

Во всех подходах внутри окна используется одна и та же модель (совместная спектральная кластеризация, параметры `model.alpha` и `model.k`), различается только связь между окнами. W_t это affinity matrix окна t.

- **Независимая кластеризация** каждого окна. Кластеры соседних окон сопоставляются венгерским алгоритмом по коэффициенту Жаккара.
- **Evolutionary clustering с фиксированным весом прошлого** (Chakrabarti et al. 2006): S_t = a S_{t-1} + (1 - a) W_t, кластеризуется S_t. Перебираются a из `dynamics.past_weights`.
- **AFFECT** (Xu, Kliger, Hero 2014): та же формула, но вес прошлого оценивается в каждом окне как a_t = сумма var(w_ij) / сумма [(s_ij - E[w_ij])^2 + var(w_ij)], где s_ij из S_{t-1}, а среднее и дисперсия w_ij оцениваются по блокам текущего разбиения. Оценка и кластеризация повторяются `dynamics.affect_iterations` раз.
- **Многослойная сеть** (Mucha et al. 2010): матрицы всех окон ставятся на диагональ одной большой матрицы, и каждый МО связывается со своей копией в соседнем окне ребром веса c / N, где N среднее число МО в окне. Каждая W_t нормирована на сумму 1, поэтому средняя сила узла внутри окна равна 1 / N, и c = 1 означает, что связь с прошлым такой же силы, как все связи узла внутри окна. Кластеризуется вся конструкция сразу, поэтому тип сохраняет идентичность во времени без сопоставления. МО, которых нет в каком-то окне, просто не имеют там копии.
- **Фиксированная типология**: типы строятся один раз по средней affinity matrix, затем в каждом окне МО относится к ближайшему центру типа в пространстве признаков.

## Как сравниваются подходы

На МО, которые есть во всех окнах, для каждого подхода считаются:
- качество каждого окна: средние по окнам SW в пространстве признаков и MQ на графе потребления;
- плавность: доля МО, сменивших тип между соседними окнами и между первым и последним окном, и ARI между разбиениями.

Хороший подход сохраняет качество окон, как у независимой кластеризации, и при этом не перебрасывает МО между типами без изменений в данных. Результат в `results/dynamics_approaches.csv`.

## Выбор

Используется многослойная сеть с c = 1 (`dynamics.coupling`). Это наименьшая связь, при которой история получается связной: при c = 0.1 и 0.3 кластеры распадаются по окнам. При этом качество окон не хуже, чем у независимой кластеризации. Чувствительность к c показана для значений из `dynamics.couplings`.

## Уточнение типов во времени

После многослойной сети к типам каждого окна применяется шаг уточнения модели (см. [methods.md](methods.md)). Если уточнять окна по отдельности, пограничные МО переходят между типами туда и обратно от окна к окну: связь между окнами есть в многослойной сети, но не в уточнении. Поэтому стоимость типа для МО в окне t усредняется по всем окнам u, где этот МО есть, с весами s^|t - u|, где s = `dynamics.smoothing`: соседнее окно весит s, окно через одно s^2. При s = 0 окна уточняются независимо, при s = 1 у МО во всех окнах один тип. Центры типов в каждом окне свои. Строка `supra 1.0 + refinement` в `results/dynamics_approaches.csv` показывает, как уточнение меняет качество окон и плавность.
